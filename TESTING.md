# Testing

How module-viewers is verified. `task-viewer` is a Rust binary on axum and sqlx. Design is `ARCHITECTURE.md`, behaviour is `FEATURES.md`, and constraints are `SECURITY.md`.

## Test Design Principles

- Test observable behaviour: parsed rows, chart series, HTTP host checks, and database contents. Where the behaviour depends on process-wide state that a parallel-safe test must not change, such as the inherited git environment or the server's working directory, assert how harvest configures its `git` command instead.
- Keep tests deterministic, isolated, offline, and parallel-safe. Every test owns its state through a per-test temp dir named `task-viewer_<name>_<pid>_<nanos>_<n>`, taken from `unique_temp_dir` in an inline test and from the process-level test's own helper, since `src/test_support.rs` opens `#![cfg(test)]` and `task-viewer` declares no lib target. Tests share no paths, no env overrides of the test process, and no execution-order assumptions, and a process-level test sets its child's environment per spawn. `cargo test` runs them in parallel.
- Cover the success path and one failure path for a behaviour that can fail.
- A test that passes a wall-clock deadline for process work carries the measured process-start latency that justifies it, and warms the stand-in or retries rather than guessing a constant; the measured worst case and the load it was taken under live beside the deadline.
- Match a status, a variant, or a field. Avoid asserting a whole error string when a variant is enough, and assert the stored message when that message is the contract.

## Test Organization

- Tests live in `#[cfg(test)]` modules in the source file they exercise, except a process-level test that spawns the built binary, which lives in `task-viewer/tests/` and reaches that binary through `env!("CARGO_BIN_EXE_task-viewer")`; the launcher tests, which live in `task-viewer/src/launcher_tests.rs` behind `#![cfg(test)]` and drive `scripts/task-viewer.sh` through a bash subprocess; and a shell suite that drives a shell entry point, which lives in `scripts/tests/*.sh` and builds its own throwaway root and home for each case.
- Shared helpers live in `#[cfg(test)]` `src/test_support.rs` (`unique_temp_dir`) for the inline suites, while the process-level test carries its own temp-dir helper on the same pattern. The `[dev-dependencies]` block in `task-viewer/Cargo.toml` adds `tower` with its `util` feature for `tower::ServiceExt::oneshot` tests through `router(state)`, and `rquickjs` for tests that execute the shipped JavaScript. A JavaScript fixture shared by those tests sits in `task-viewer/testdata/`, such as `testdata/browser_guards.js` with its stub DOM: it is the JavaScript counterpart of the `src/test_support.rs` helpers, kept outside `src/` so it adds no Rust module. Those tests run the shipped `static/js/theme-boot.js`, `static/js/theme.js`, and `static/js/dashboard.js` against the fixture, and `theme-boot.js` carries its own storage-throwing test beside the theme toggle's.
- Database tests set a thread-local database path under a unique temp dir and use the current-thread runtime so that path stays on the test thread, while a test that spawns work onto other threads uses the multi-thread flavor and still opens its pool on the test thread, since every spawned task takes the pool from `AppState` instead of opening the database itself, and a process-level test that spawns the built binary sets `TASK_VIEWER_DB` in its own per-test temp dir for that child process and needs neither.
- Git tests build a unique temporary repository with `user.email` and `user.name` passed on the command, and with author and committer dates in the environment.

- `make format` runs rustfmt.
- `make lint` runs clippy with warnings denied.
- `make test` runs `cargo test` with warnings denied, then `scripts/tests/launcher-build-truth.sh`, which drives copies of the launcher and installer in throwaway roots and homes: the locked build command in the launcher and `make build`, the missing-cargo failure, rustup cargo winning over a Homebrew-first PATH, one build per toggle, the installer's icon-cache and desktop-database checkmarks, a build failure before the atomic swap leaving the previous bundle intact, a failed `sips` resize printing the icon-skip message and installing the PNG, a failing `dockutil` and a failing `defaults import` each printing the manual-pin guidance, a clean install replacing the bundle and pinning it, a successful swap whose backup cleanup fails reporting the leftover backup directory and still finishing clean, a successful restore whose backup cleanup fails reported as a plain restored-bundle failure, not a failed restore, the detach branch without python3, and the pinned toolchain. Every launcher case pins `XDG_STATE_HOME` under its own root, and each case that keeps `/usr/bin` on `PATH` also keeps failing `osascript` and `notify-send` stubs first on it, while the two detach cases instead drop the desktop tools entirely by running with only their own minimal `bin` directory on `PATH`. The suite asserts that a decoy sentinel state directory stays untouched, that the PID and stamp files resolve under the case root, and that a `status` run invokes neither stub. It then runs `scripts/tests/launcher-state-dir.sh`, which drives the launcher with a home it cannot write, with a state-directory path that is a regular file, and with a state directory that turns unwritable so the lock loop must stop, each in a throwaway root and home, and checks that a writable state directory still serves `status` and releases the lock. It then runs `scripts/tests/audit-gate.sh`, which drives the vendored-tree digest check and the rsa check against throwaway git roots and a fake `cargo`.
- `make audit` runs `cargo audit`, the `vendor/sqlx-sqlite.sha256` verification, and the `cargo tree -i rsa` reachability check when dependencies change.
