# Make the narrow-width charts readable

## Goal

The calendar and radar charts stay readable, not merely non-negative, when their frame is narrow, and the layout strategy behind that is an explicit decision rather than the accident of a positive floor.

## Context

The archived `tasks/archive/task-viewer_browser-robustness.md` clamped the calendar cell size and the radar radius to a positive minimum, so no rect carries a negative width and no circle a negative radius. That satisfied its Acceptance, which stopped at valid geometry.

The residual behaviour, measured against the shipped formulas:

- `calendar` in `task-viewer/src/series.rs` always starts at today minus 364 days, so the calendar holds ~53 columns however old the repository is. `drawCalendar` in `task-viewer/static/js/dashboard.js` computes `cell = Math.max(1, Math.min(14, Math.floor((width - labelW - 8) / columns) - 2))` with `gap = 2`, so the last column starts at `labelW + 52 * (cell + gap)`. That exceeds the viewBox width whenever the frame is narrower than about 187px: at 120px the cell floors to 1, the pitch becomes 3, and the newest ~22 columns fall outside the 120-unit viewBox.
- `drawRadar` computes `radius = Math.max(1, Math.min(width, height) / 2 - 64)`, so below about 128px the radar collapses to a 1px radius and its labels sit at `radius + 16` around the center.
- Month labels are drawn once per month, not once per column: `drawCalendar` emits a label only for a column whose first cell satisfies `first.date.getDate() <= 7`, at `x = labelW + col * (cell + gap)`. Across ~53 columns that is about twelve labels at an average pitch of roughly four columns, and they still overlap once `cell` floors to 1 and the pitch becomes 3 units, because an 11px month name is tens of units wide.
- Cells are placed at `18 + row * (cell + gap)`, so a small cell leaves most of the 190px-tall frame empty.
- `.chart-frame svg` sets `width: 100%`, so the viewBox is stretched to the frame and anything outside it is clipped rather than scrollable.

No normal browser viewport reaches the 120px case; it is reachable through the test stub and through a very narrow embedded pane. The work is therefore about a stated responsive strategy and about proving it, not about an observed production failure.

## Approach

Pick one strategy per chart, record the reason in a code comment, and make the strategy testable. The evidence supports two different answers because the two charts have different natures.

- Calendar: scroll horizontally. A contribution-style heatmap has a natural width, so set the viewBox width to the natural content width (`labelW` plus `columns * (cell + gap)` plus 8px of padding, the same 8px the shipped formula's `- 8` term already allows) and let `.chart-frame.calendar` scroll horizontally when that exceeds the client width. Set `cell` to a fixed 14 and keep `gap` at 2, both independent of the frame width, so a narrow frame scrolls full-size cells rather than a 1px strip. A fixed 14 reproduces today's layout only from an 884px-wide frame upward, where the shipped formula already yields 14: with `labelW` 28, 53 columns, and 8px of padding the calendar's natural width is 884px (`28 + 53 * 16 + 8`), so the natural width and the 884px cell threshold coincide, and every frame narrower than 884px both renders a larger cell than it does today and scrolls rather than fitting. Set the SVG element's `width` attribute to that same natural width in pixels, and change the `.chart-frame.calendar svg` rule in `static/style.css` to `width: auto` so it stops inheriting `width: 100%` from `.chart-frame svg`; the chart then renders at 1:1 and `.chart-frame.calendar` scrolls horizontally when the natural width exceeds the client width. Add `overflow-x: auto` to a `.chart-frame.calendar` rule and `min-width: 0` to the base `.chart-card` rule in `static/style.css` (the base rule rather than `.chart-card.wide`, so the plain radar cards share the opt-out), because `.charts` is a grid whose items default to `min-width: auto`: without `min-width: 0` the calendar SVG's natural width becomes the wide card's min-content width, the grid track grows to it, `.chart-frame.calendar` is never narrower than its SVG, and the page overflows horizontally instead of the frame scrolling. This is the standard treatment for a calendar heatmap and preserves the daily semantics, the cell size, and the 11px label size. Rejected alternatives: shrinking `gap` to 0 fits 53 columns into 84px but leaves a 1px-per-cell strip that is unreadable, and scaling the whole viewBox down shrinks the text to illegibility.
- Calendar labels: keep the existing month-boundary gate (`first.date.getDate() <= 7`) so each label stays on its own month's first week and keeps the correct month name, and thin within that set — drop a month's label when its column would sit closer than 24px to the last label actually drawn — so consecutive rendered labels sit at least 24px apart. 24px is the legibility floor for the shipped 11px font: a three-letter month label is about 18px wide, so 24px leaves a visible gap, and it stays well below the ~64px monthly pitch the normal-width frame already produces, so normal width is untouched.
- Radar: fit to the frame by expanding the viewBox, not by shrinking the label margin, and render the expanded chart at 1:1 rather than letting `width: 100%` scale it. A radial chart has no natural width, so derive the radius from the smaller frame dimension minus the shipped 64px label margin, floor it at 31px — the largest floor Acceptance 4 permits, because the shipped formula yields 31px in the stub's 190px-high frame at 1000px width, so the floor binds only below that width and never raises the normal-width radius — and keep every label inside the viewBox by setting the viewBox to the label ring's bounds measured per axis: horizontally the anchor at `radius + 16` plus half the width of an 18-character label at 11px (59.4), so the ring width is `2 × radius + 150.8`, and vertically the same anchor plus an 11px glyph's ascent above its baseline (8.8, at 0.8 em), taken as the conservative half-height on both sides, so the ring height is `2 × radius + 49.6` — the ascent rather than half a line height, because `drawRadar` emits each label with `y` at its baseline and `text-anchor: middle` centers it horizontally only; the ring height then stays 111.6 at the 1000×190 stub frame, inside the frame, so the fits branch remains reachable. The ring fits the frame-sized viewBox when its width and height are each no larger than the frame's; at normal width the frame height `2 × radius + 128` clears the ring height, so the fit turns on the frame being at least 22.8 units wider than it is tall. Compute the radius from the frame dimensions before that expansion, so the expansion never feeds back into the radius. When the label ring already fits the frame-sized viewBox, leave the viewBox at the frame size and clear both of the element's inline `style.width` and `style.height`, so it keeps its inherited `width: 100%` and the `.chart-frame.radar svg` `height: 360px`; the normal-width layout renders at 1:1 and is unchanged. When the ring does not fit, settle the element's used size in both axes with inline styles — `svg.style.width = ringWidth + "px"` and `svg.style.height = ringHeight + "px"`, the same inline-style mechanism `tipFor` already uses — and give `.chart-frame.radar` `overflow-x: auto`, so a narrow frame scrolls the full-size chart instead of scaling it down into the frame. An inline style outranks every author rule, including `.chart-frame svg`'s `width: 100%` and `.chart-frame.radar svg`'s `height: 360px`, so the used width and height are exactly the ring size and the expanded viewBox renders at 1:1 instead of being sized from the 360px CSS height; that scroll engages because the base `.chart-card` rule carries the `min-width: 0` the calendar bullet adds, which the plain radar cards need since they carry no `wide` class. Leave the `.chart-frame.radar svg` rule in `static/style.css` unchanged. At a 1000px frame the ring fits, the floor does not bind, the 64px margin is untouched, and the radius equals the shipped formula, so the normal-width layout is unchanged. Rejected alternative: reducing the label margin, which moves the label ring outward and cannot fit an 18-character label at a 120px frame.

Measure a text label's extent as its anchor plus its character count times 6.6px at `font-size` 11, the conservative advance that covers the 18-character radar truncation: a `start`-anchored label extends right by that width and a `middle`-anchored one by half of it. A label fits when its horizontal extent stays inside the viewBox on both sides and its vertical extent stays inside the viewBox top and bottom, where the vertical extent runs from 8.8 units above the label's baseline to 8.8 units below it; the tests use these extents in place of an unmeasurable glyph box.

Tooltip: settle it as `position: fixed`, placed from the pointer's viewport coordinates (`tip.style.left = event.clientX + 12 + "px"` and `tip.style.top = event.clientY + 12 + "px"`), and drop the `frame.getBoundingClientRect()` lookup and its `bounds` local from `tipFor`. A fixed-position tooltip takes the viewport as its containing block, and `static/style.css` declares no `transform`, `filter`, `contain`, or `perspective` on any ancestor, so the scrolling calendar frame neither clips the tooltip nor shifts it by `scrollLeft`. The line chart's overlay keeps its own `svg.viewBox.baseVal.width` conversion for the viewBox change.

**Out of scope:** changing the calendar's 365-day window or the daily bucketing, and adding a chart library.

## Acceptance

- A test drives the stub DOM at a 120px frame with the `year_of_calendar_rows` fixture and asserts that the calendar's viewBox width is its natural content width, that the SVG element's `width` attribute equals that same natural width so the chart renders at 1:1 rather than scaling into the frame, that every calendar rect carries width and height 14, and that every rect, and every month label's measured extent, lies inside that viewBox.
- A test reads `static/style.css` as source text and asserts that `.chart-frame.calendar` declares `overflow-x: auto`, that `.chart-frame.calendar svg` declares `width: auto`, and that the base `.chart-card` rule declares `min-width: 0`, so the wide calendar cards and the plain radar cards shrink below their chart's intrinsic width and each frame scrolls instead of the page overflowing.
- A test reads `static/style.css` and `task-viewer/static/js/dashboard.js` as source text and asserts that `.tooltip` declares `position: fixed` and that `tipFor` places the tooltip from the pointer's viewport `clientX`/`clientY` without a `getBoundingClientRect` lookup, so the scrolling calendar frame neither clips nor offsets the tooltip.
- A test at a 120px frame asserts that the radar's radius is at least 31px and that every radar label's measured extent lies inside the viewBox on both axes, horizontally within its left and right edges and vertically from 8.8 units above the label's baseline to 8.8 units below it, so the label at the top of the ring is not clipped by the frame-sized viewBox.
- A test at a 120px frame and a test at a 1000px frame each assert the radar's rendered scale is 1:1 in both axes, computed from the size the element actually takes: at 120px the element's inline `width` and `height` styles divided by the viewBox width and height are each 1, and those inline values equal the ring's natural size; at 1000px the element carries no inline size and the stub's `clientWidth` divided by the viewBox width is 1. Because an inline style outranks the stylesheet's `width: 100%` and `height: 360px`, this reads the used size rather than a declaration a CSS rule can override, so an expanded viewBox is never scaled down into the frame and the 11px labels keep their size. A test reads `static/style.css` as source text and asserts that `.chart-frame.radar` declares `overflow-x: auto`, so a narrow frame scrolls the full-size chart.
- A test at a 1000px frame asserts the calendar cell size is 14 and the radar radius matches the shipped formula, so the layout at or above the calendar's 884px threshold is unchanged.
- A test at an 800px frame, driving the `year_of_calendar_rows` fixture (53 columns), asserts that the calendar's viewBox width is its natural content width and that the SVG element's `width` attribute equals that width, so a mid-width frame below the 884px threshold scrolls the full-size chart instead of shrinking the cell to fit. The stub in `task-viewer/testdata/browser_guards.js` gains a numeric `config.width` (120 when `config.narrow` is set, 1000 otherwise) so a third frame width is expressible, and this test passes that width.
- A test at a 120px frame, driving the `year_of_calendar_rows` fixture (53 columns), asserts that the rendered month labels are spaced at least 24px apart.
- A test reads `task-viewer/static/js/dashboard.js` as source text and asserts it carries one comment stating the calendar's layout strategy and one stating the radar's, each naming the strategy it chose and the reason for it.
- Every `web.rs` test that runs the shipped scripts through `run_browser` keeps passing.
