# Shut down on SIGTERM without cutting off a running Update

## Goal

When the launcher stops the server, or a person presses Ctrl-C under `make run`, the server stops accepting connections, lets an Update that is already storing finish within a bounded grace period, closes the database, and exits on its own before the launcher's forced kill. An Update that completes inside the grace period keeps every row it harvested, where today the process dies at once and discards them. The launcher's state-file documentation names every file the launcher writes.

## Context

`main` in `task-viewer/src/main.rs` runs under `#[tokio::main]`, builds the `AppState`, and awaits `axum::serve(listener, app)` with no shutdown future and no signal handler, so SIGTERM ends the process immediately. The stop path in `scripts/task-viewer.sh` sends `kill`, polls `is_running` ten times at 0.5-second intervals, and then sends `kill -9`, so the server has five seconds to exit by itself.

Update runs inside a detached task that holds `state.scan` from listing the repositories through the last store, as `ARCHITECTURE.md` describes under **Load-Bearing Decisions**. Harvests run on blocking threads and can each hold a git child for up to the git deadline. Returning from an async `main` drops the tokio runtime, and that drop waits for every blocking task without a bound, so a plain graceful return could outlast the launcher's window and still end in `kill -9`. A store already interrupted is safe today: each repository's `replace_tasks` is one transaction, and WAL rolls an unfinished one back on the next open.

`tokio::signal` needs tokio's `signal` feature, which the current `features = ["full"]` includes. The archived, deferred `task-viewer_build-efficiency` plan lists a trimmed tokio feature set without `signal`, so reviving that plan after this task lands has to keep `signal`.

`SECURITY.md` under **Data** says the launcher keeps "its PID file and the server log" in its per-user state directory and that "both files are mode `600`", and `README.md` describes the same two files. The launcher defines four files there (`PID_FILE`, `LOG_FILE`, `BUILD_LOG`, and `STAMP_FILE`), creates them under `umask 077`, and repairs older modes with a `chmod 600` line that lists the first three and leaves out `STAMP_FILE`.

## Approach

1. Add a function in `task-viewer/src/web.rs` that serves a router until a given shutdown future resolves and then drains within a given grace period. It takes one deadline when the shutdown future resolves, stops accepting through `axum::serve(..).with_graceful_shutdown(..)`, waits for open connections and for `state.scan` under that deadline, and then awaits `state.pool.close()` under the time that deadline has left, dropping the close when the deadline is already spent and leaving that store to the WAL rollback `## Context` describes. It returns that deadline to its caller. Production passes a grace period of 4 seconds, one second inside the launcher's window.
2. In `main.rs`, build the tokio runtime explicitly in place of `#[tokio::main]`, run that function with a shutdown future that resolves on SIGTERM (through `tokio::signal::unix` on Unix) or on Ctrl-C, log one line when the signal arrives, and end with `Runtime::shutdown_timeout(web::remaining(deadline))` over the deadline the serve function returns, so a blocking harvest cannot hold the process past that deadline. `web::remaining` returns the time left to a deadline and zero once it has passed, so the runtime wait is the remainder of the same grace the serve call works inside rather than a fresh one. `main` reads the listen port from `TASK_VIEWER_PORT` when set and otherwise uses `web::PORT`, still binding `127.0.0.1`; that read is a test-only override, marked as such by a comment at the read site, and the host allowlist, the same-origin `Origin` check, and every documented `7880` stay derived from `web::PORT`, so an isolated test runs the built binary on a free loopback port beside a running dashboard while what a browser reaches stays unchanged.
3. Add `"$STAMP_FILE"` to the launcher's `chmod 600` repair line.
4. Rewrite the **Data** paragraph of `SECURITY.md` and the matching `README.md` sentence so each names every launcher state file — the PID file, the server log, the build log, and the binary stamp — with every one at mode `600`. Add a **Load-Bearing Decisions** bullet to `ARCHITECTURE.md` stating the signal handling, the 4-second grace period, its relation to the launcher's 5-second stop window, and the dependence on tokio's `signal` feature. Rewrite the first **Test Organization** bullet in `TESTING.md` so it reads that tests live in `#[cfg(test)]` modules in the source file they exercise, except a process-level test that spawns the built binary, which lives in `task-viewer/tests/` and reaches that binary through `env!("CARGO_BIN_EXE_task-viewer")`; rewrite `TESTING.md` in place so its rules hold for both test locations: in **Test Design Principles**, the sentence "Every test owns its state through a per-test temp dir from `unique_temp_dir` (`task-viewer_<name>_<pid>_<nanos>_<n>`)" comes to read that every test owns its state through a per-test temp dir of that name, taken from `unique_temp_dir` in an inline test and from the process-level test's own helper, since `src/test_support.rs` opens `#![cfg(test)]` and `task-viewer` declares no lib target; the **Test Organization** bullet "Tests live in `#[cfg(test)]` modules in the source file they exercise" comes to read that tests live in `#[cfg(test)]` modules in the source file they exercise, except a process-level test that spawns the built binary, which lives in `task-viewer/tests/` and reaches that binary through `env!("CARGO_BIN_EXE_task-viewer")`; and that section's shared-helpers bullet comes to read that `src/test_support.rs` holds the inline suites' helpers (`unique_temp_dir`) while the process-level test carries its own temp-dir helper on the same pattern, its remaining text unchanged; the **Test Organization** bullet "Database tests set a thread-local database path under a unique temp dir and use the current-thread runtime so that path stays on the test thread" comes to read that database tests set a thread-local database path under a unique temp dir and use the current-thread runtime so that path stays on the test thread, while a process-level test that spawns the built binary sets `TASK_VIEWER_DB` in its own per-test temp dir for that child process and needs neither; the **Test Design Principles** clause "Tests share no paths, no env overrides, and no execution-order assumptions" comes to read that tests share no paths, no env overrides of the test process, and no execution-order assumptions, and a process-level test sets its child's environment per spawn; add a **What Must Be Covered** bullet stating that SIGTERM and SIGINT each let an in-flight store finish and the process exit inside the launcher's window; and refresh that `TESTING.md` line in both root rule files that carry it, `AGENTS.md` and its `CLAUDE.md` twin, so each names both the inline modules and the process-level test.

**Out of scope:** Changing how the launcher starts or stops the server, which stays as the archived `task-viewer_launcher-ps-portability` task left it.

## Acceptance

- A `web` test runs the serve function with a oneshot as its shutdown future while a stand-in scan holds `state.scan`, fires the shutdown, releases the lock after a short delay inside the grace period, and finds that a connection opened to the listener after the shutdown fires is refused while the drain still waits, that the function returns after the release, and that the pool is closed.
- A `web` test holds `state.scan` past a short grace period passed to the same function and finds that the function returns within that grace period plus a small margin.
- A `web` test holds a store open past a short grace period passed to the same function, by pointing `state.store_hook` at a hook that signals it is inside `replace_tasks` and then waits, and finds that the function returns within that grace period plus a small margin.
- A `web` test runs the serve function with a shutdown future while a real Update stores through the store hook, fires the shutdown inside the grace period, and finds the repository's rows present after the function returns.
- A test in `task-viewer/tests/` spawns the built binary through `env!("CARGO_BIN_EXE_task-viewer")` with `TASK_VIEWER_DB` in a per-test temp dir and `TASK_VIEWER_PORT` on a free loopback port, waits until a `GET /` carrying `Host: 127.0.0.1` answers `200`, sends SIGTERM, and finds the process exits on its own with a success status inside the launcher's five-second window; it then repeats the spawn, signal, and wait with SIGINT; `TESTING.md`'s **Test Organization** admits that process-level test and its **What Must Be Covered** carries the graceful-shutdown bullet, and its **Test Design Principles** temp-dir sentence and its **Test Organization** shared-helpers bullet each name the process-level test's own per-test temp dir, its **Test Organization** database-test bullet admits the process-level test's per-spawn `TASK_VIEWER_DB`, its **Test Design Principles** env clause limits "no env overrides" to the test process, and the `TESTING.md` line in `AGENTS.md` and in `CLAUDE.md` names both test locations.
- A `web` test fires the shutdown future of a serve call and finds that the deadline the function returns falls inside the grace period after the signal, and that `web::remaining` of a deadline four seconds ahead, one second ahead, and already passed returns a larger remainder, a smaller one above zero, and zero.
- `scripts/task-viewer.sh` repairs the mode of `STAMP_FILE` alongside the other three files.
- `SECURITY.md` and `README.md` each name every launcher state file, and the "both files" wording is gone from both.
- `ARCHITECTURE.md` carries one **Load-Bearing Decisions** bullet naming the signals, the 4-second grace period, and the `signal` feature.
