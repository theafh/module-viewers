# Features

What `task-viewer` does, from the person's side. Structure is `ARCHITECTURE.md`, constraints are `SECURITY.md`, and `TESTING.md` is the verification floor.

## 1. Product Scope

- Runs in a browser on the same machine as the binary, with no account and no upload.
- Serves on `127.0.0.1:7880`.
- Reads repositories the person selects. Those repositories stay where they are.
- Stores the repository list and the parsed task rows in `~/.task-viewer`. `TASK_VIEWER_DB` names a different database file: spaces around the value are ignored so a padded value opens the same file, and a value that is not valid UTF-8 is refused at start-up with that variable named. The database is created or upgraded on launch, two launches against one file take turns upgrading it instead of wedging each other, and an upgrade that fails leaves the version the file already had so the next launch retries it. A file already stamped at the current schema version that lacks a table or a column the code selects is refused at start-up with the database path, version, table, and column named, instead of starting and failing every page. A database file that is not task-viewer's is refused at start-up instead of being adopted: a non-empty file carrying a table or column no task-viewer schema version has, or missing a table or column its stamped version must have while carrying one that version cannot, fails with the database path and the offending table or column named and needs an empty file or a new path, while a file matching an older task-viewer version still migrates and an empty or missing file initializes and carries the task-viewer `application_id`. On Unix the file this build opens is mode `0600`, as are its `-wal` and `-shm` sidecars, while a file it refuses keeps the mode it was found with.
- The browser caches the styles, scripts, and icon between visits. Every `/static` URL carries a version derived from the asset bytes as read when the server starts, so a changed asset gets a new URL and the browser never serves a stale one, while the HTML pages themselves are never cached. The version is fixed for the process lifetime, so editing a static asset needs a server restart before the browser sees the new bytes.
- `make install` installs a macOS Dock or Linux application-menu icon that toggles the server (start if stopped, stop if running). Each start, and each icon click, first builds the release binary at `target/release/task-viewer` from the checkout (a no-op when nothing changed), so the server always runs the checked-out code. An icon click builds once. When the build produced a binary newer than the running server, start and the icon click restart the server on it. When the build fails, start reports it and runs nothing, and an icon click on a running server stops it; a missing `cargo` counts as a failed build and names `make build`. A start with neither `python3` nor `setsid` available refuses with an explanation and runs nothing, instead of leaving a server that dies with the launcher. One launcher command runs at a time: `start`, `stop`, `status`, `restart`, and `toggle` take an exclusive lock, so two invocations cannot race the PID file and only the lock holder removes one. A state directory the launcher cannot create or make private fails the command with a message naming it and a non-zero exit before any lock is attempted, and a lock that can be neither taken nor reclaimed ends the same way after a bounded wait instead of spinning. The launcher recognizes its own server whether `ps` prints the binary as an absolute path (a checkout path holding a space included), a path relative to the checkout, a bare name on `PATH`, or a task-viewer release binary at any other checkout's path, a moved or renamed checkout included, with trailing arguments allowed; it reports the started-from path when that differs from this checkout's binary, and it signals only such a process: a stop aimed at an unrelated PID sends it no signal. A stop reports success only after the process is gone, so a server that survives the forced kill fails the stop with a non-zero exit instead of reading as stopped. A start that never gets its server onto the port terminates the process it launched. `PORT` moves both the bind and the URL the launcher prints, while the server answers the bare loopback names as well as their 7880 host forms, so the dashboard is browser-reachable on 7880 alone: the launcher drops an inherited `TASK_VIEWER_PORT` and passes its own port to the server. `make start` / `make stop` / `make status` drive the same launcher. `status` exits 0 while the server runs and 1 while it does not, so a script can branch on it the way it would on `systemctl is-active`; the running branch prints the PID line, the `Access at:` URL, and, when the server was started from another path, the started-from line, while the stopped branch prints one line, and the exit code carries the answer. On macOS a reinstall builds the new `Task Viewer.app` in a hidden `.Task Viewer.app.staging.*` directory beside the installed bundle and swaps it in only after its executable and `Info.plist` exist, so a failed install before the swap leaves the previous app usable and the installed path is never empty; a failed install can leave that staging directory beside the bundle, a restore that itself fails leaves the previous bundle in the `.Task Viewer.app.backup.*` directory the installer names, and a successful swap whose backup cleanup fails leaves that backup directory behind and names it. When the icon build fails, the install reports that the icon build was skipped and copies the PNG into Resources instead, so the bundle still carries an icon; when the Dock pin fails, it prints how to add the app by hand instead of a traceback. The pin runs only from the login account's own home: an install with a redirected `HOME`, or one whose account home cannot be determined, still installs the bundle and prints that manual guidance without reading or writing `com.apple.dock`, `TASK_VIEWER_DOCK_PIN=force` pins from any home, and `TASK_VIEWER_DOCK_PIN=skip` skips the pin.

## 2. Navigation

- The sticky bar carries Dashboard and Repositories tabs, plus the theme control. The app opens on Dashboard. Every page wraps its content in a main landmark with the tab bar above it, so assistive technology can skip the bar and land on the page's own content.
- On Dashboard, the bar also carries the project filter and Update, and beside them one Export control whose menu holds the Charts CSV and Charts JSON links that export the chart data of the selected project. The control is a native `<details>` whose summary reads `Export`, so the menu opens without scripting and both links stay server-rendered. Choosing a project submits the filter at once, so switching projects is one click; a page without scripting keeps a Show button, which the script hides once it attaches that submit-on-change listener. Update submits as a normal form so the browser follows the redirect and shows the one-shot outcome banner exactly once; while the browser waits for that scan the Update button disables and reads `Updating…` and the charts section carries `aria-busy`, and a `pageshow` restores both when the browser re-enters the page from its cache. A page that loads while a scan is already running reads `GET /status` once and then once a second until `scanning` reads false, marks the page busy the same way, and names how many repositories are configured; the scan line beside it is written only when its text changes, so the polite live region announces a new count instead of repeating the same sentence on every poll.
- On Repositories, the bar carries Add repository.
- Every one-shot outcome banner carries a live-region role: a notice banner carries `role="status"` and an error banner carries `role="alert"` on the dashboard, the Repositories page, and the Remove confirmation page, so the outcome is announced without moving focus.
- All projects is the default filter.
- Light and Dark switch the page. The theme control names the theme it switches to, reading "Light Mode" while the dark theme is applied and "Dark Mode" while the light theme is applied. Without scripting the nav carries a second control, a form that posts the opposite theme and the page's own path and query to `POST /theme`, which sets the `task_viewer_theme` cookie (`Path=/`, a one-year `Max-Age`, `SameSite=Lax`) and returns to that path percent-encoded — a space as `%20`, each non-ASCII UTF-8 byte as its own `%XX`, and an existing `%XX` escape and a `+` kept as they are — so a page without scripting switches and every page renders the cookie's theme, `light` or `dark` and dark otherwise, until the choice changes; the inert script button is hidden. The switch writes both the stored choice and the cookie, so the script and no-script paths agree: a browser that blocks storage still remembers the choice through the cookie, one that blocks cookies still remembers it through the stored choice, and only a browser that blocks both the stored choice and the cookie keeps the switch for the session alone, applying it and recoloring the charts until the page is left. An explicit stored choice wins over the cookie, which wins over the operating system's colour scheme, so a later no-script choice survives scripting only when no stored choice exists, and a first visit with neither follows the OS, opening the light theme on a light preference. A no-script browser that blocks cookies cannot persist a switch, so every page it loads renders the default dark theme.

## 3. Repositories

- The Repositories tab lists each repository's name, path, last successful scan time, its most recent scan error with that error's own time, its stored row counts, and whether that error is current. The error line words that state, reading `last error (current) <time>: <message>` while the repository is failing and `last error (recovered) <time>: <message>` once a later success has cleared it, so the state never rests on colour alone; a stored error with no error time renders `last error (current): <message>` or `last error (recovered): <message>` with no time, and a repository with no stored error renders no error line. A later success keeps the stored error as history, so a recovered repository shows both stamps and renders the error as muted history, while a repository whose most recent scan failed renders it as an error. Each name links to the dashboard filtered to that repository. A scanned repository shows how many rows it contributes and how many of those are live, read with one grouped select over the stored rows, and a repository with neither a success nor an error reads `not scanned yet` in place of a scan time and its counts. The Added and scanned stamps this build writes are UTC instants written with a `Z` designator; a row stored by an older build keeps the spelling it was stored with, and every stamp renders as a human local time with a relative `N days ago` once the stamp's UTC day is at least one day before today's. A stamp that does not parse keeps its raw text.
- Add repository opens a folder picker. A folder is accepted when its working tree contains `tasks/`, or when a branch of the repository that holds it carries a markdown task under `tasks/`, so a checkout without `tasks/` is still accepted when another branch holds it. Dismissing the picker cancels the add with no error, while a picker that fails reports the fixed `picker-failed` code: the picker's own stderr goes to the server log and never into the redirect. A folder whose working tree and refs hold no `tasks/` reports "That folder has no tasks directory.", a folder this process cannot read reports `folder-unreadable` with the real error logged, and a picked path that is not valid UTF-8, or a pick whose canonical path is not, is refused with `path-not-utf8` instead of being stored lossily. After add or remove, the person stays on Repositories. Add reports a failed first harvest as a scan error on the new repository instead of as a success, which covers a `tasks/` symlink that points outside the picked folder: the probe accepts the folder and the first harvest reports the outside target as a scan error. A request that disconnects mid-add does not cancel the store: the insert and its first harvest keep the scan lock and finish storing, so the repository and its rows are there on the next read, and a second Add or an Update waits for that store rather than racing it.
- Remove opens a confirmation page the server renders at `GET /repositories/{id}/delete`. The page names the repository and its folder, carries a form that posts to the same path, and carries a Cancel link back to Repositories, so a browser without scripting deletes nothing until that form is posted. The POST drops that repository and its parsed rows from `~/.task-viewer`; an id that no longer exists renders the not-found outcome on the confirmation page and reports `repository-not-found` from the POST instead of claiming a removal.
- Each repository row carries Rescan, which harvests and stores only that repository's rows through the same path Update uses, leaves every other repository's rows and scan stamp untouched, and reports `repository-scanned` on Repositories. A repository whose `tasks/` tree is missing, or whose git history or files cannot be read, reports the same fixed code Update would store for it. The route is `POST /repositories/{id}/scan`, and an id that no longer exists reports `repository-not-found` without harvesting anything.
- Each repository row also carries Relocate, which opens the folder picker and moves that repository to the picked folder. The pick is canonicalized and probed for `tasks/` exactly as Add probes it, a path another repository already stores is refused with `repository-path-taken` and leaves both repositories unchanged, and the repository keeps its id and its stored rows, which are re-harvested from the new folder under the scan lock so the row carries a fresh scan stamp. The route is `POST /repositories/{id}/path`; an id that no longer exists reports `repository-not-found` without moving anything. A request that disconnects mid-relocate does not cancel the store: the lookup, the collision check, the path write, and the re-harvest keep the scan lock and finish storing, so the repository reads the new folder with a fresh scan stamp, and a second Relocate or an Update waits for that store rather than racing it. Relocate is the fourth refresh path beside Update, Add, and Rescan.
- Add warns before it stores a second clone of a configured repository. Each repository is identified by its canonical origin URL, trimmed with one trailing `/` and `.git` dropped, or, for a repository with no remote, by its canonical git common directory, which is what two worktrees of one repository share; a folder with no git identity of its own is never a duplicate. A match stores nothing: the page names the repository it duplicates and offers a Confirm form, and only `POST /repositories/confirm/{token}` stores the held path, at most once. A request that disconnects mid-confirm does not cancel the store: taking the token and storing the held path keep the scan lock and finish, so the repository and its first harvest's rows are there on the next read, and a second Confirm or an Update waits for that store rather than racing it. The exact-path refusal stays, so adding the same folder twice still reports `repository-exists`.
- Update scans every configured repository, up to `TASK_VIEWER_SCAN_WORKERS` at once (a whole number from 1 to 32, default 4; a larger value is clamped to 32, and a value below 1 or one that is not a number falls back to 4 with a warning), and replaces the parsed rows that still read cleanly. A read-only git command that runs past `TASK_VIEWER_GIT_TIMEOUT_SECS` (default 30 seconds; a whole number of seconds from 1 to 600 is used as given, a larger value is clamped to 600, and a value below 1 or one that is not a number falls back to 30 seconds) fails that repository's scan. A repository whose git history cannot be read, or whose `tasks/` tree holds a directory that cannot be read, keeps its rows and shows a scan error. A `tasks/` folder that is a symlink charts its tasks under `tasks/...` paths when the link's target stays inside the configured folder, and fails the repository's scan with a scan error, keeping its rows and logging the path and the outside target, when the link points outside that folder. A directory symlink under `tasks/` is followed when its resolved target stays inside the configured folder, so the tasks below it chart under their `tasks/...` paths; one whose target leaves the folder, a broken link, and a link loop each warn once naming the link path and, when it has one, the target, chart no row, and leave the rest of the scan charting, and a task-shaped broken link still counts in the skipped-file total. An enclosing-repository probe that fails for a reason other than git's not-a-repository answer fails the scan, with git's first stderr line in both the logged error and the stored repository message, which opens with the fixed git-history sentence and cuts the reason at 200 characters. A repository whose clone is shallow fails its scan with a message that starts with `git fetch --unshallow` and names the configured folder by its basename, including a configured subfolder with no `.git` of its own inside the shallow clone; it keeps its rows, stores the scan error shown on Repositories, and clears its stored history key, so a rescan after `git fetch --unshallow` charts the real archive day, while a shallow probe that cannot run fails the scan instead of reading as "not shallow". A failed git history read also clears the stored history key, so the next scan re-walks instead of reusing a day the failed read could not verify. The dashboard reports the run truthfully: it shows the success notice only when every repository harvested, and otherwise names each failed repository and its reason. The success notice also names what changed against the rows the run replaced: how many task rows appeared for the first time and how many gained a ship day since the last scan, and it leaves those counts out when nothing changed. A task is matched by its file name, so finishing a task, which moves its file under `tasks/archive/`, counts as shipped rather than as a new task. That outcome is shown once, on the first dashboard read, and a reload shows nothing; a first read cancelled before it renders puts the outcome back for the next read. An Update with no configured repository reports that there was nothing to update, and a stopped Update or a repository list that cannot be read shows its banner once in the same way. A repository with a git history is read from its working tree and every branch, so a task counts whether or not its branch is checked out, except that a regular working-tree task file that cannot be read, is not valid UTF-8, or is larger than 4 MiB is skipped, still claims its task name, and therefore suppresses an older committed copy of the same task. A markdown entry under `tasks/` charts only when it is a regular file or a symlink whose resolved target is a regular file inside the configured folder: a symlink that dangles or points outside, and a directory, FIFO, socket, or other non-regular entry named like a task, is skipped without being opened, logs one warning, and claims no task name, so a committed copy of the same name still charts. A task file that is not valid UTF-8 or is larger than 4 MiB contributes no row, whether the working tree or a committed blob supplied it. Such a skipped file does not fail the scan, and the other tasks chart normally. A markdown file under `tasks/` charts only when its name has the task shape — a `.md` name carrying an `_` behind a non-empty scope prefix — and its frontmatter carries a parseable `created` and a non-empty `status`; a file whose name fails that shape, such as a `README.md` or a `_draft.md`, charts no row and no radar spoke, adds nothing to the skipped-file total, and logs at debug level, while a shaped file with bad frontmatter still warns and counts once. A task file with a UTF-8 BOM, leading blank lines, a frontmatter opener carrying trailing whitespace, quoted frontmatter values, a quoted status padded with spaces inside its quotes, a space-separated timestamp, or a trailing `#` comment on a frontmatter value charts like its plain spelling. A task file with an empty `status:` charts no row and logs one warning naming its path, and one whose `updated` value does not parse charts on its `created` day and logs one warning naming the path and the raw value. A task file whose name holds a backslash, a glob character, or a byte that is not valid UTF-8 still charts: the backslash stays part of the stored path, a glob name dates only from its own commits, and a non-UTF-8 name charts under its lossy path with the frontmatter `updated` day as its leave day. A request that disconnects mid-scan does not cancel the run: the scan keeps the scan lock and stores every harvested result, so the next Update or Remove waits for it to finish instead of racing harvests that still run. Clicks that arrive while a scan runs share one follow-up scan, which starts after the running scan finishes and reads the repositories only after it starts. A stop or Ctrl-C lets an Update that is already storing finish inside a four-second grace period, and the server then exits on its own instead of dying at once. An Update that skipped task files appends how many to its banner, on the success and failure message alike.
- The dashboard header states the freshness of what it charts: it names the oldest successful scan stamp among the repositories in scope and appends the count of repositories in scope that are stale, where a repository whose most recent scan failed and a repository whose stamp does not parse each count as stale. A success after an error clears the repository's failing and stale state while its stored error stays visible as history. A stamp that does not parse proves no freshness: when no in-scope stamp parses but at least one is stored, the line reads `Last scan unknown`, and `Not scanned yet` is reserved for a scope whose repositories carry no stamp at all. Each repository in scope whose most recent scan failed renders that cause on the dashboard as well as on Repositories.
- `GET /status` is the JSON the dashboard polls while a scan runs: `scanning` (whether the scan lock is held), `worker_cap`, `repositories` (how many are configured), `last_scan` (the newest parseable scan stamp, or `null`), and `failed_repositories` (how many repositories' most recent scan failed). It is served with `Cache-Control: no-store` like every other page route.

## 4. Charts

The dashboard shows ten charts from the stored rows, for all configured repositories or for the one selected. A header line above the charts names how many repositories are in scope, the task totals the charts are built from (tasks, live, deferred, and finished), and the as-of day. Every chart day is a UTC calendar day, and a timestamp with no zone is read as `Europe/Berlin`:

- Weekly shipped, created, and deferred over the last 104 Monday weeks ending in today's week, an event before that window is cut rather than folded, bars stacked from one baseline in the order the view names, each bar centred in its own week's slot and no wider than that slot, and the summary totals summing the drawn weeks. A View picker on the card redraws that card alone between all three stacked (the default), only shipped, only created, only deferred, and shipped plus deferred stacked without created; the summary names only the series the chosen view draws.
- Cumulative tasks shipped, with a dashed trend; a one-day series draws a filled dot at its value and says `Not enough days yet` instead of an empty line.
- Tasks shipped over the last 365 days, laid out in Monday-through-Sunday rows, colour `log1p(count)`; the first month label carries its year.
- Tasks created over the last 365 days, laid out in Monday-through-Sunday rows, colour `log1p(count)`; the first month label carries its year.
- Live backlog size by day, with a dashed trend; a one-day series draws a filled dot at its value and says `Not enough days yet`.
- Mean age in days of the unfinished backlog, with a dashed trend; a one-day series draws a filled dot at its value and says `Not enough days yet`. Finished and deferred tasks leave that average on their archive leave day; a deferred leave day after today counts as today, so the average drops the task the same day the backlog and the weekly deferred bar do, while a finished task keeps its own ship day. A finished row whose stored ship or leave day does not parse leaves on its other day, then its updated day, then its created day, with ship equal to leave; a deferred row whose leave day does not parse leaves on its updated day, then its created day. They never count as shipped when deferred.
- Cycle time, the mean days from a task's `created` day to its ship day over the tasks that finished on each charted day, with a dashed trend, a task count, and a one-day series that draws a filled dot and says `Not enough days yet`. A ship day after today counts as today, so a future-dated ship contributes `today - created` days, floored at zero when `created` is itself after today. A deferred task and a finished task with no ship day contribute nothing, and a ship day before `created` counts from the created day as a zero-day cycle.
- Live-task staleness, up to three lines counting live tasks whose stored `updated` day lies at least 30, 90, or 180 days behind each charted day, counted from the task's created day onward; a live task whose task file carries no `updated:` value, or an `updated` value that does not parse, is charted from its `created` day, so it starts counting on each line that many days after it was created, and a task that charts no row counts on no line. A threshold that stays zero across the whole window gets no line, and a card with no stale task says so instead of drawing flat lines. A legend above the plot puts a tiny dot in each line's colour before its label, and the summary and tooltip name only the drawn thresholds.
- Shipped radar, four rings labelled with their values on its own peak, rounded up to a multiple of four with a floor of four, so every ring label is a whole number.
- Live radar, four rings labelled with their values on its own peak, so a live count of 35 fills the chart instead of being flattened against a shipped peak of 300. The summary names the spoke kind the rows carry: one spoke per repository with all projects selected, one per task scope with one project selected, and the rows decide when a payload carries no mode.
- Every chart card carries an icon-only download control pinned to its upper-right corner, named for assistive technology by its per-chart `aria-label` and given the hover text `Download PNG` by its `title`, and a page without scripting keeps it hidden. A click rasterizes that card's drawn chart in the browser, in the current theme: the card's background is laid behind the drawn SVG, the image is drawn at twice the SVG's size, and the download is named `task-viewer-<chart>-<as-of>.png`. The drawn chart stays as it is, and no server round trip is made. A download that cannot load, draw, or encode the image shows `Download failed` beside the control and announces it in that card's own polite status region, and a later successful download or a redraw clears the message.

Hovering or focusing a mark shows that mark's count — a week's shipped, created, or deferred bar, a day, or a spoke — and activating a shipped or created bar, a day, or a spoke opens the task list filtered to the rows behind that count: the page's project, the task kind, the day axis, and the window, while a radar spoke in the All-projects view carries its repository and kind, a radar spoke in the single-project view carries the page's project, kind, and scope, and neither carries a window. The deferred weekly bar names its count without a drill-down link, because the list filters on created and ship days and no filter reproduces a leave-day count. A chart's marks form one tab stop, and the arrow keys step the focus through them; a line chart's overlay takes the one tab stop and its arrow keys step through the drawn days, and a calendar's tab stop sits on its newest day whenever the frame scrolls, or on its first day when the frame fits the whole calendar. A tooltip hides when the chart is redrawn, when the weekly View picker changes the series, and when the page or a chart frame scrolls, so no stale count outlives the mark it described; a redraw hides a hover or pointer tooltip, while a redraw that restores a mark's focus shows a fresh tooltip through that mark's `focus` listener, and a tooltip a mark's focus shows is exempt from the scroll hide, because the scroll that brings the focused mark into view must not hide the count focus just showed, and it still hides on blur. A page without scripting keeps a Loading chart text in each frame and says the charts need scripting, naming the Repositories link. With all projects selected, each radar spoke is one repository. With one project selected, each spoke is one task scope, the filename prefix before the first underscore. Each chart is named by its card heading and described by its summary line. A theme switch recolours the drawn charts in place.

`GET /tasks` is the read-only list a chart mark opens. It shows each stored row's repository, scope, path, kind, created day, and ship or leave day, sorted by any of those six columns in either direction and defaulting to scope then path with the path breaking every tie, states how many rows the current filter matched, and links back to the dashboard on the same project. It accepts `project` (a repository id, or all), `kind` (`live`, `finished`, `deferred`, or all), `scope`, `q` (a case-insensitive substring of the path), `date` (`created` or `shipped`, naming the day axis the `from` and `to` bounds apply to), `from`, `to`, `sort` (`repository`, `scope`, `path`, `kind`, `created`, or `day`), and `dir` (`asc` or `desc`), where an unknown `sort` or `dir` falls back to the default. Each header links to the same filters sorted by that column, the active header carries `aria-sort` and an arrow, and clicking it again reverses the direction; a row with no ship or leave day sorts last ascending and first descending. One server-rendered GET form on the page carries a search input bound to `q` and a scope select bound to `scope`, whose options are the current project's distinct scopes plus All scopes and, when the request applies a scope the project does not store, that applied value marked selected, so the control always shows the scope the list filters on, with a Show button, while the project, kind, date, from, to, sort, and dir filters ride along as hidden fields, so a filtered and sorted view stays linkable and works without scripting. An Export CSV link carries the same filters and the resolved sort to `GET /tasks.csv`, which serves the same filtered rows in the list's order as `text/csv; charset=utf-8` with an attachment disposition and a header row of repository, scope, path, kind, created, ship day, and leave day; a finished row's day lands in ship day, a deferred row's in leave day, and a field holding a comma, a quote, or a line break is wrapped in double quotes with each inner quote doubled, and a field that opens with `=`, `+`, `-`, `@`, a tab, or a carriage return is prefixed with one single quote, so a cloned repository whose folder, scope, or path carries a formula lead character opens in a spreadsheet as text instead of being evaluated. Charts CSV and Charts JSON links sit beside Export CSV, and the dashboard's navigation bar carries the same two links inside one closed Export control's menu beside the project filter and Update, each carrying the selected project alone to the two chart exports. Above the table, a list with an applied kind, day axis and window, search text, or scope names those filters in a readable summary and offers one removable chip per filter beside a Clear link; a chip re-requests the list without its own filter while keeping the project, the other filters, and the current sort and direction, Clear drops every filter and the order while keeping the project, and a request whose values the filter ignores, such as `kind=all` or a windowless `date=created`, names no filter and renders no summary. The list never edits, finishes, or deletes a task file.

`GET /charts.json` serves the dashboard's own chart payload for the selected `project` as an attachment named `charts.json`, so a saved payload is the one the page drew from, and `GET /charts.csv` serves the same series in long format as a `text/csv; charset=utf-8` attachment named `charts.csv`: the fixed header `series,key,value`, then one row per point, where a weekly point writes its week day for the `created`, `shipped`, and `deferred` bars, cumulative, backlog, mean age, and cycle time write their day for the level and a `<series>_trend` row for the fit, each calendar writes its day, staleness writes its day once per threshold, and each radar writes its spoke label. Both accept the dashboard's `project` filter, absent or `all` meaning All projects, and both apply the task export's CSV quoting and formula rule to the `series` and `key` columns alone, while the numeric `value` column is written as a plain number that keeps its sign, so a negative trend exports as `-0.06` instead of a quoted `'-0.06`. A project with no stored rows exports the CSV header alone and a payload whose event series are empty.

A card whose chart cannot be drawn shows Charts unavailable in place of the chart and in its summary line, and the other cards still render.
