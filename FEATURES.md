# Features

What `task-viewer` does, from the person's side. Structure is `ARCHITECTURE.md`, constraints are `SECURITY.md`, and `TESTING.md` is the verification floor.

## 1. Product Scope

- Runs in a browser on the same machine as the binary, with no account and no upload.
- Serves on `127.0.0.1:7880`.
- Reads repositories the person selects. Those repositories stay where they are.
- Stores the repository list and the parsed task rows in `~/.task-viewer`. `TASK_VIEWER_DB` names a different database file: spaces around the value are ignored so a padded value opens the same file, and a value that is not valid UTF-8 is refused at start-up with that variable named. The database is created or upgraded on launch, two launches against one file take turns upgrading it instead of wedging each other, and an upgrade that fails leaves the version the file already had so the next launch retries it.
- The browser caches the styles, scripts, and icon between visits. Every `/static` URL carries a version derived from the asset bytes as read when the server starts, so a changed asset gets a new URL and the browser never serves a stale one, while the HTML pages themselves are never cached. The version is fixed for the process lifetime, so editing a static asset needs a server restart before the browser sees the new bytes.
- `make install` installs a macOS Dock or Linux application-menu icon that toggles the server (start if stopped, stop if running). Each start, and each icon click, first builds the release binary at `target/release/task-viewer` from the checkout (a no-op when nothing changed), so the server always runs the checked-out code. An icon click builds once. When the build produced a binary newer than the running server, start and the icon click restart the server on it. When the build fails, start reports it and runs nothing, and an icon click on a running server stops it; a missing `cargo` counts as a failed build and names `make build`. A start with neither `python3` nor `setsid` available refuses with an explanation and runs nothing, instead of leaving a server that dies with the launcher. One launcher command runs at a time: `start`, `stop`, `status`, `restart`, and `toggle` take an exclusive lock, so two invocations cannot race the PID file and only the lock holder removes one. The launcher recognizes its own server whether `ps` prints the binary as an absolute path, a path relative to the checkout, or a bare name on `PATH`, with trailing arguments allowed, and it signals only such a process: a stop aimed at an unrelated PID sends it no signal. A stop reports success only after the process is gone, so a server that survives the forced kill fails the stop with a non-zero exit instead of reading as stopped. A start that never gets its server onto the port terminates the process it launched. `PORT` moves both the bind and the URL the launcher prints, while the server answers the bare loopback names as well as their 7880 host forms, so the dashboard is browser-reachable on 7880 alone: the launcher drops an inherited `TASK_VIEWER_PORT` and passes its own port to the server. `make start` / `make stop` / `make status` drive the same launcher.

## 2. Navigation

- The sticky bar carries Dashboard and Repositories tabs, plus the theme control. The app opens on Dashboard.
- On Dashboard, the bar also carries the project filter and Update.
- On Repositories, the bar carries Add repository.
- All projects is the default filter.
- Light and Dark switch the page. The browser remembers the choice, except where a restricted browser blocks storage: the switch still applies for the session and recolors the charts, it just is not remembered for the next visit.

## 3. Repositories

- The Repositories tab lists each repository's name, path, last scan time, and any scan error. An unscanned repository reads `not scanned yet` in place of a scan time. The Added and scanned stamps this build writes are UTC instants written with a `Z` designator; a row stored by an older build keeps the spelling it was stored with.
- Add repository opens a folder picker. A folder is accepted when its working tree contains `tasks/`, or when a branch of the repository that holds it carries a markdown task under `tasks/`, so a checkout without `tasks/` is still accepted when another branch holds it. Dismissing the picker cancels the add with no error, while a picker that fails reports the fixed `picker-failed` code: the picker's own stderr goes to the server log and never into the redirect. A folder whose working tree and refs hold no `tasks/` reports "That folder has no tasks directory.", a folder this process cannot read reports `folder-unreadable` with the real error logged, and a picked path that is not valid UTF-8 is refused with `path-not-utf8` instead of being stored lossily. After add or remove, the person stays on Repositories. Add reports a failed first harvest as a scan error on the new repository instead of as a success. A request that disconnects mid-add does not cancel the store: the insert and its first harvest keep the scan lock and finish storing, so the repository and its rows are there on the next read, and a second Add or an Update waits for that store rather than racing it.
- Remove drops that repository and its parsed rows from `~/.task-viewer` after confirmation. A remove whose id no longer exists reports that the repository was not found instead of claiming a removal.
- Update scans every configured repository, up to `TASK_VIEWER_SCAN_WORKERS` at once (a whole number from 1 to 32, default 4; a larger value is clamped to 32, and a value below 1 or one that is not a number falls back to 4 with a warning), and replaces the parsed rows that still read cleanly. A read-only git command that runs past `TASK_VIEWER_GIT_TIMEOUT_SECS` (default 30 seconds; a whole number of seconds from 1 to 600 is used as given, a larger value is clamped to 600, and a value below 1 or one that is not a number falls back to 30 seconds) fails that repository's scan. A repository whose git history cannot be read, or whose `tasks/` tree holds a directory that cannot be read, keeps its rows and shows a scan error. An enclosing-repository probe that fails for a reason other than git's not-a-repository answer fails the scan, with git's first stderr line in the logged error message and the fixed git-history message on the repository. The dashboard reports the run truthfully: it shows the success notice only when every repository harvested, and otherwise names each failed repository and its reason. That outcome is shown once, on the first dashboard read, and a reload shows nothing. An Update with no configured repository reports that there was nothing to update, and a stopped Update or a repository list that cannot be read shows its banner once in the same way. A repository with a git history is read from its working tree and every branch, so a task counts whether or not its branch is checked out, except that a working-tree task file that cannot be read, is not valid UTF-8, or is larger than 4 MiB is skipped, still claims its task name, and therefore suppresses an older committed copy of the same task. A task file that is not valid UTF-8 or is larger than 4 MiB contributes no row, whether the working tree or a committed blob supplied it. Such a skipped file does not fail the scan, and the other tasks chart normally. A task file with a UTF-8 BOM, leading blank lines, a frontmatter opener carrying trailing whitespace, quoted frontmatter values, a quoted status padded with spaces inside its quotes, a space-separated timestamp, or a trailing `#` comment on a frontmatter value charts like its plain spelling. A task file with an empty `status:` charts no row and logs one warning naming its path, and one whose `updated` value does not parse charts on its `created` day and logs one warning naming the path and the raw value. A task file whose name holds a backslash, a glob character, or a byte that is not valid UTF-8 still charts: the backslash stays part of the stored path, a glob name dates only from its own commits, and a non-UTF-8 name charts under its lossy path with the frontmatter `updated` day as its leave day. A request that disconnects mid-scan does not cancel the run: the scan keeps the scan lock and stores every harvested result, so the next Update or Remove waits for it to finish instead of racing harvests that still run. Clicks that arrive while a scan runs share one follow-up scan, which starts after the running scan finishes and reads the repositories only after it starts. A stop or Ctrl-C lets an Update that is already storing finish inside a four-second grace period, and the server then exits on its own instead of dying at once.

## 4. Charts

The dashboard shows eight charts from the stored rows, for all configured repositories or for the one selected. Every chart day is a UTC calendar day, and a timestamp with no zone is read as `Europe/Berlin`:

- Weekly shipped versus created, Monday weeks, shipped above the axis and created below.
- Cumulative tasks shipped, with a dashed trend.
- Tasks shipped over the last 365 days, colour `log1p(count)`.
- Tasks created over the last 365 days, colour `log1p(count)`.
- Live backlog size by day, with a dashed trend.
- Mean age in days of the unfinished backlog, with a dashed trend. Finished and deferred tasks leave that average on their archive leave day; they never count as shipped when deferred.
- Shipped radar.
- Live radar.

Hovering a mark shows the count for that week, day, or spoke. With all projects selected, each radar spoke is one repository. With one project selected, each spoke is one task scope, the filename prefix before the first underscore.

A card whose chart cannot be drawn shows Charts unavailable in place of the chart, and the other cards still render.
