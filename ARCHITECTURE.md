# Architecture

How module-viewers is structured and where that structure is headed. This document describes the system. Identity is `CHARTER.md`, behaviour is `FEATURES.md`, constraints are `SECURITY.md`, and verification is `TESTING.md`.

## System Overview

module-viewers is a Cargo workspace of local viewers. `task-viewer` is a single Rust binary that serves a browser UI on `127.0.0.1:7880`. There is no account and no background daemon. The person starts the binary and it serves until they stop it.

The git tree holds the program. The SQLite file `~/.task-viewer` holds the repository list and the parsed task rows that the charts read. `TASK_VIEWER_DB` overrides that path for a test or a private location. `TASK_VIEWER_SCAN_WORKERS` caps how many repositories Update harvests at once: a whole number from 1 to 32 is used as given, a larger value is clamped to 32, and a value below 1 or one that is not a number falls back to the default of 4 with a warning. `TASK_VIEWER_GIT_TIMEOUT_SECS` changes the deadline for one read-only git command and defaults to 30 seconds: a whole number of seconds from 1 to 600 is used as given, a larger value is clamped to 600, and a value below 1 or one that is not a number falls back to 30 seconds with a warning. `RUST_LOG` sets the log filter and defaults to `task_viewer=info`. `TASK_VIEWER_PORT` overrides the listen port, and the binary reads it on every build, release included. The launcher drops an inherited value and exports its own port, so a shell's or a test's value never reaches the server it starts. A non-default port is for an isolated test, which runs the built binary on a free loopback port beside a running dashboard; the address stays `127.0.0.1`, and the host allowlist and the same-origin `Origin` check stay derived from the default port, so a server on another port binds but rejects every request whose `Host` names that port. `TASK_VIEWER_TEST_STORE_PAUSE_MS` is test-only and unset everywhere else: a whole number of milliseconds holds a store open that long inside the write transaction, so a process-level test can signal the server while a store is in flight, and `TASK_VIEWER_TEST_STORE_MARKER` names the file that pause writes once it begins, so the test waits for the store to be open instead of betting on a delay. `TASK_VIEWER_TEST_CHART_BARRIER_DIR` and `TASK_VIEWER_TEST_CHART_BARRIER_COUNT` are test-only and unset everywhere else: a positive whole-number count makes each `GET /charts.json` render write a marker file named by its thread id into that directory and wait there until the directory holds that many markers or a ten-second deadline passes, so a process-level test can hold several chart exports in flight together and prove a warning fires once per process rather than once per thread. Nothing in the database is required to build or run the program for the first time. The first launch creates an empty database.

## Stack

- Language: Rust (edition 2024), `unsafe_code` forbidden, clippy `unwrap_used`, `float_cmp`, and `format_push_string` denied.
- Web: axum, Tera templates, static assets under `task-viewer/static/`.
- Storage: SQLite via sqlx, WAL journal mode, `synchronous=NORMAL`, foreign keys on.
- Runtime: tokio.
- Charts: browser SVG drawn from a JSON payload the server builds out of the task rows.

## Components

**`task-viewer/src/main.rs`** binds `127.0.0.1:7880`, or the port named by `TASK_VIEWER_PORT` on that same loopback address, opens the database, and starts the router.

**`task-viewer/src/web.rs`** owns the routes. The dashboard is `GET /`. The theme choice is `POST /theme`; it sets the `task_viewer_theme` cookie (`Path=/`, a one-year `Max-Age`, `SameSite=Lax`) and redirects to a safe local `next` percent-encoded — a space as `%20`, each non-ASCII UTF-8 byte as its own `%XX`, and an existing `%XX` escape and a `+` kept as they are; every page renders that cookie's `light` or `dark` theme, dark otherwise. The task list is `GET /tasks`; it renders the stored rows for the current filter — repository, scope, path, kind, created day, and ship or leave day — and never writes a task file. Its CSV export is `GET /tasks.csv`; it returns the same filtered rows as an attachment with seven columns — repository, scope, path, kind, created day, ship day, and leave day — so the list's numbers can leave the page. The chart series leave the page the same way: `GET /charts.json` serves the dashboard's own payload for the selected `project` as an attachment, and `GET /charts.csv` serves the same series in long format with the header `series,key,value`, one row per point; both build through the same selection and payload function the dashboard renders from, so the page and the exports cannot drift. The repository list is `GET /repositories`. Add repository is `POST /repositories` and opens the operating-system folder picker on this machine. Remove is `POST /repositories/{id}/delete`; `GET /repositories/{id}/delete` renders the confirmation page that names the repository and its folder and carries the form posting to that same path, so a browser without scripting deletes nothing until the form is posted. Rescan one repository is `POST /repositories/{id}/scan`; it re-harvests and stores that repository alone. Relocate is `POST /repositories/{id}/path`; it opens the same folder picker, canonicalizes and probes the pick as Add does, refuses a canonical path that is not valid UTF-8, refuses a path another repository already stores, writes the new path for that id, and re-harvests that repository alone under the scan lock so its rows survive and read the new folder. Confirming a duplicate clone is `POST /repositories/confirm/{token}`; it stores the path Add held in a one-shot slot on `AppState`, so a clone is stored only after the person confirms it and no path rides the redirect. `GET /status` returns the scan state as JSON — `scanning`, `worker_cap`, `repositories`, `last_scan`, and `failed_repositories` — for the dashboard's poll while a scan runs. Update is `POST /scan`; it harvests up to the configured cap at once and stores each result one repository at a time. Routes name a repository by its integer id. The folder path is taken from the picker, not from the browser body.

**`task-viewer/src/harvest.rs`** reads `tasks/**/*.md`, reads frontmatter, and asks git for the leave day of each finished or deferred task. It returns the parsed rows together with a reason-keyed tally of the task files it skipped, and does not write them. A harvest that fails carries the tally it had recorded before the failure, so a scan error still counts the skips that preceded it.
**`task-viewer/src/db.rs`** creates the parent directory of the database file, whether that file is the default `~/.task-viewer` or a path named by `TASK_VIEWER_DB`, opens the database, and brings its schema to the current version one step at a time. The version read, the version-1 baseline, and every later step run inside one `BEGIN IMMEDIATE` transaction on one connection, so two processes starting against one file serialize their migration instead of both stamping it, and a step that fails rolls the whole run back and leaves the version the file already had. That transaction opens before the version read, so every start takes SQLite's write lock even when the schema is already current, and a start that lands while another process holds the lock waits out the five-second busy timeout and fails with `the database at … could not begin its schema migration` instead of opening read-only. The step that adds `content_hash` is guarded on the table's own columns, so a file stamped below that step which already carries the column still migrates, and the version-4 step that adds `last_error_at` and `last_outcome` is guarded the same way, as is the version-5 step that adds `repositories.history_key`. Before the baseline and again before each later step, the same transaction reads the file's tables from `sqlite_master` and their columns from `pragma_table_info` and refuses a file that is clearly not task-viewer's: one carrying a table or column no task-viewer version has, or one missing a table or column its stamped version must have while carrying one that version cannot have, fails start-up with the database path and the offending table or column named and says an empty file or a new path is needed. A file matching an older task-viewer version still migrates, extra later columns with nothing required missing are accepted so a half-applied file still migrates, and a newly created baseline is stamped with `PRAGMA application_id = 0x5456_0001` (the ASCII `TV` and a format number) so an external reader inspecting a copy can recognize the file. Once the loop reaches the current version, a verification pass reads each expected table and column from `sqlite_master` and `pragma_table_info`, so a file already stamped at that version which lacks a table or a column the code selects fails start-up naming the database, the version, the table, and the column instead of starting and answering every page with a 500. On Unix, the file it opens is mode `600` whether it creates it or finds it already there, and a `-wal` or `-shm` sidecar already beside it is tightened to `600` too while a sidecar SQLite creates later copies that mode, so the repository and task paths the file holds stay owner-only; a file this build refuses — a foreign schema, a newer stamp, or an unreadable version — keeps the mode it was found with, an existing parent directory keeps its own mode, and the change is a no-op on a non-Unix target. It reads and writes the two tables.

**`task-viewer/src/series.rs`** turns the stored rows into the ten chart series for the current filter, including the weekly deferred bar, the live-task staleness lines, and the mean cycle time of the tasks that finished on each day.

## Data Layout

```text
~/.task-viewer    # the SQLite database file; db.rs creates its parent directory
  repositories    # table: name, absolute path, created_at, last scan, last error and its time, last outcome, history key
  tasks           # table: parsed rows for one repository, replaced on update
```

`tasks` stores the relative path, the scope (filename prefix before the first underscore), the kind (`finished`, `deferred`, or `live`), `created`, `updated`, `ship_date`, `leave_date`, and `content_hash`, the hash of the file bytes the row was parsed from together with the frontmatter reader revision that parsed them, so a reader change invalidates every stored row once. Update reuses a row's stored leave day only while its path and `content_hash` still match the file, the repository's stored `history_key` still equals the history this harvest reads, and that stored day came from a commit, and walks git again when the bytes change, when the key differs, or when the stored day is the frontmatter `updated` fallback because no commit carries the archived status — an uncommitted archive or a history git cannot see. The history key is the repository's identity by the same rule Add uses for a folder with its own `.git` (the canonical `origin` URL, otherwise the canonical git common directory), the configured folder's place inside that repository, and the sorted tip commit ids of the ref set `git log --all` walks — every ref under `refs/*` plus `HEAD`, with an annotated tag peeled to its commit. A folder without its own `.git` takes the identity from its resolved enclosing repository, so the key can carry the enclosing repository without changing `repository_identity`. The stored value is a fixed-width digest of those parts, so an `origin` URL that carries an embedded credential is never written to the database. A key mismatch ignores every cached day for that repository, so relocating to a clone whose origin or ref tips differ re-walks the archived paths instead of reusing a day from a history the dashboard no longer reads. A failed git read or a shallow refusal clears the stored key, so the next scan re-walks rather than reusing a day the failed read could not verify. A folder outside git has no history key and keeps the `updated` fallback. A fallback day on a lossy path is the exception: that path names no git object, so no later commit can date it, and the stored day is reused until the file's bytes change or the history key changes instead of being re-walked on every Update. Chart series are computed from these rows when the dashboard renders. A stored `ship_date` or `leave_date` that does not parse logs one warning naming the repository, path, field, and raw value, once per process, and never drops the row: a finished row ships on its leave day when its ship day is missing, then takes its leave day from the ship day, the stored `updated` day, or `created`, and keeps ship equal to leave, while a deferred row takes its leave day from `updated`, then `created`, and a live row keeps no day. A deferred row's weekly bar sits on that fallback day, because the bar is counted by leave day. Update deletes and reinserts the rows of each repository whose working tree holds a `tasks/` directory or whose refs list a markdown task under it. A repository that holds neither keeps its previous rows and records the missing-tasks error, and an unreadable directory keeps them the same way.

## Extraction Rules

- A configured repository that has a git history — its own `.git` or an enclosing repository's — is charted from every version of its `tasks/` tree that the working tree or any local or remote-tracking ref holds, so a task stays on the charts whichever branch is checked out. An enclosing repository is listed under the configured folder's prefix, so its own root `tasks/` never enters the listing and every stored path stays relative to the configured folder. A task is identified by its file name and counts once; the working tree outranks a commit, then an archived path outranks a live one, then the newest commit decides, read with merges diffed against their first parent (`--diff-merges=first-parent`), so a task version that only a merge commit produced is dated from that merge commit. The ref union holds each `(path, blob)` pair once, so a repository that keeps one branch per task grows its listing by each branch's edited task instead of by the whole `tasks/` tree per branch, while a ref whose `tasks/` subtree id is already listed costs no recursive listing. A folder outside git is charted from its files. A task file whose content is not valid UTF-8 contributes no row, whether the working tree or a committed blob supplied it, so one such file cannot fail its repository's scan. A task file larger than 4 MiB contributes no row, whether the working tree or a committed blob supplied it, so one oversized file never sits in memory whole. The working-tree walk keeps the text it read for the chosen rows only while that retained total stays within 8 MiB, so a larger `tasks/` tree re-reads the rows it evicted, one file at a time and still bounded by the 4 MiB cap. An evicted row is re-read through the real on-disk path the walk recorded beside its lossy stored path, so a file name that is not valid UTF-8 is re-read from its file instead of dropped, and the size its warning reports comes from that same path. The working-tree path is built from the path's components with `/` separators rather than from one lossy string with backslashes rewritten, so a file name holding a literal backslash keeps that backslash in its stored path and charts once instead of splitting into two rows. A file name that is not valid UTF-8 still charts: the committed listing and the working-tree walk both decode it lossily to the same path, so the two candidates dedupe to one row. A markdown entry under `tasks/` contributes a row only when it is a regular file or a symlink whose resolved target is a regular file inside the configured folder: a directory, FIFO, socket, or other non-regular entry named like a task, and a symlink that dangles or resolves outside the folder, contributes no row, is never opened, logs one warning naming its path and the outside target when it has one, and claims no task name, so a committed task of the same name still charts. A `tasks/` folder that is a symlink is charted only when its resolved target stays inside the configured folder, and the walk stays on the `tasks/` path itself so every stored path keeps its `tasks/...` shape; a link whose target lands outside the folder fails that repository's scan with an error naming the `tasks/` path and the outside target, so the repository keeps its prior rows instead of charting markdown from outside the folder.
- `created` is the UTC day of the frontmatter `created` timestamp of every task file, including tasks that are later deferred.
- `finished` means the file is under a directory named `archive` and its status is `finished`. Any other archived status is `deferred`. A file outside `archive` is `live`.
- The leave day of a finished or deferred task is the UTC day of the committer timestamp of the earliest commit that archives it. For a finished task that is the earliest commit whose path lies under a directory named `archive` and whose content at that commit carries `status: finished` or `status: implemented`, so the commit that first moves the file into `archive/` qualifies even when it edits no status literal, and a later bulk rename of `implemented` to `finished` does not move the day. For a deferred task it is the same archived-path walk keeping only content that carries `status: deferred`, so a deferral made while the task was live does not move the day, while an archived status other than `finished` or `deferred` dates from the earliest commit whose frontmatter carries it, for any accepted spelling — bare, single- or double-quoted, or padded inside either quote style. The pickaxe finds the candidate commits and one `git cat-file --batch` reads each `<commit>:<path>` back, so a `status:` line in a body example, a table, or a quoted snippet is skipped and only a commit whose frontmatter carries the status dates the task; a task first written `status: "open"` and later rewritten `status: open` keeps the earlier commit's day. The archive walk runs `git -c log.showSignature=false -c log.decorate=false -c log.showRoot=true log -z --follow --diff-merges=first-parent --name-only --format='%cI %H' --all -- <rel>` and reads each commit id at either SHA-1 or SHA-256 length. With `-z` git prints each path raw, so a task file name or a folder path holding a non-ASCII character or a double quote still matches, and a record whose path holds a newline is skipped, because `cat-file` reads one expression per line. The archive walk and the pickaxe pass their path as `:(literal)<rel>`, so a task name holding `*`, `?`, `[`, or a backslash matches only that file instead of a glob or an escape. The walk tests each path against the folder's place at that commit — the current prefix when it held a `tasks` tree there, otherwise its nearest ancestor at a path-component boundary that did, and never the enclosing repository root for a folder below it — so a folder renamed or moved to a different depth keeps its first archive day, a nested `tasks/` tree inside the folder and a sibling tree's archive still date the task, and an `archive` directory above the folder's place does not count. One `git cat-file --batch` reads every archived-path `<commit>:<path>`, and an expression that names no object, whether a deletion commit or a path that is not valid UTF-8 produced it, answers `missing` and counts as no qualifying commit; the walk keeps the earliest date whose frontmatter status is the one it looks for, `finished` or `implemented` for a finished task and `deferred` for a deferred task. The walk takes names and content instead of patch lines, so a date line in a patch cannot become the leave day. It reads every commit whose path lies under `archive` rather than stopping at the newest, so renames still match. Lookups run from the repository folder with that repository's `--git-dir` / `--work-tree`, so neither an inherited `GIT_DIR` nor the server's working directory can redirect them. Plain `-C` is the fallback when that folder has no `.git` or the first command fails to run; a lookup that runs and finds nothing stops there. Merge commits are diffed against their first parent (`--diff-merges=first-parent`), so a task archived while resolving a merge still matches. When git runs and returns nothing, which happens when the archived status is not committed yet or when the path cannot be named in a git command, the frontmatter `updated` day is the leave day; a folder outside any git repository takes that day too. A task whose name is not valid UTF-8 charts under its lossy path, which carries a `\u{FFFD}` replacement character; that path names no object, so the task keeps the `updated` fallback. Two file names that decode to one lossy path store one row, the highest-ranked version on the git-backed path and the first row in path order in a folder outside git, and harvest logs one warning for that path naming the lossy path, how many harvested rows shared that path, and the fallback day. When git cannot read a folder that has a `.git` (it does not start, or both lookups exit with an error), the scan of that repository fails, its rows stay as they were, and the repository shows a scan error. The same failure stops the scan inside a resolved enclosing repository: a failed leave-day lookup in the finished/deferred archive walk `first_archived_commit_date` performs, and a failed pickaxe lookup that `git_pickaxe` runs for an archived task whose status is neither `finished` nor `deferred`, each fails the scan instead of taking the `updated` fallback, because a git failure is not the "no such commit" condition that fallback covers. Live tasks have no leave day.
- A cached leave day is reused only while the repository's stored history key matches the history this harvest reads: the repository's identity, the configured folder's place inside it, and the sorted tip commits of the ref set the archive walk reads. On a mismatch the harvest ignores every cached day for that repository and re-walks its archived paths, so a relocate to a clone whose origin or ref tips differ dates each task from the history the dashboard now reads.
- A repository whose clone is shallow fails its scan instead of charting a boundary-day guess: `git rev-parse --is-shallow-repository` runs once per repository through the bounded read-only runner, outside the folder's own-`.git` guard, so a configured subfolder without a `.git` still detects the enclosing shallow clone. The fixed message puts `git fetch --unshallow` first and names the configured folder by its basename, so the 200-character cut in the stored scan message cannot drop the fix. The failed scan keeps the repository's prior rows and clears its stored history key, so a leave day cached against the shallow history is not reused and the next full-history scan re-walks and stores the real archive days. A probe that cannot run fails the scan too, so it is never read as "not shallow"; a full-history repository and a folder outside git keep their current paths.
- The ship day of a finished task is its leave day. Deferred tasks have no ship day.
- Weeks start on Monday. A task created and shipped in the same week counts in both series.
- The cumulative and backlog charts include every calendar day from the later of their first day and 2005-04-07 through today, with earlier events counted on that first day, and the weekly chart starts at the Monday of that week; when the first event lies after today, the start also caps at today, or at today's Monday for the weekly chart. An after-today ship counts in the cumulative chart's last day, and an after-today created or ship event counts in the weekly chart's last week, so each series ends at its own count. The mean-age chart includes only the days that hold at least one unfinished task, from the later of its first such day and 2005-04-07 through today, so a day with an empty backlog carries no mean-age point. A day with no event keeps the previous level on the cumulative and backlog charts, while the mean age rises by one on such a day. 2005-04-07 is the earliest day git records a commit, so no git-backed task file can have been created earlier; a row dated before it keeps its real values, folds into the first charted point, and logs one warning naming its repository, path, and date, once per process.
- The two calendars are the last 365 days through today, laid out in Monday-through-Sunday rows. Colour is `log1p(count)`. Zero stays on the empty track.
- Live backlog adds one on `created` and subtracts one on the leave day. A leave day before `created` counts from `created`, so a record whose dates are out of order cannot leave the task in the backlog forever. A deferred task's leave day after today counts as today, the day the weekly deferred bar folds it into, so the card and the backlog agree; a finished task keeps its own ship day.
- Mean age is the average age, in days, of tasks that exist and are unfinished at the end of that day. A task drops out of that average on its leave day, and a deferred leave day after today counts as today, the same day the backlog drops it. Calendar days are UTC days: a timestamp that states `Z` or a numeric offset converts to UTC, a timestamp with no zone is read as `Europe/Berlin`, and a date-only value keeps the calendar day it names.
- The cumulative, backlog, mean-age, and cycle-time line charts carry a least-squares trend; the staleness lines draw their counts without one.
- Cycle time is the mean of the days from a task's `created` day to its ship day over the finished tasks that shipped on that day, one point per day that at least one task finished on. A ship day after today counts as today, so a mistyped future date contributes `today - created` days instead of a future span that would flatten every real value, floored at zero when `created` is itself after today. A deferred row and a finished row with no ship day contribute nothing. A ship day before `created` counts from `created`, so its point sits on the created day with a zero-day cycle. A day outside the charted range folds into the nearest bound, and the trend is fitted across the days that carry a point.
- Radar spokes share one axis order, sorted by shipped plus live, then by label. All projects uses the repository name as the label. One project uses the scope.

## Load-Bearing Decisions

- Parsed rows are the chart base, so a dashboard view does not re-walk repositories until Update, Add, a per-repository Rescan, or a Relocate.
- A duplicate clone is identified by the canonical origin URL a clone shares with the configured repository, or, for a repository with no remote, by the canonical git common directory two worktrees share; Add holds the validated path in a one-shot slot on `AppState` and stores nothing until the confirm POST takes it.
- The binary reads repository files and git history. It does not write into those repositories.
- Update runs harvests in parallel but stores their results one repository at a time, because overlapping writes would queue on SQLite's write lock, and a write that waits past the five-second busy timeout would leave its repository with old rows and a scan error. It primes the cap and then spawns the next repository only after a finished result has been stored and dropped, so the join set stays bounded at the worker cap and each repository's prior rows are read in their own stage just before its harvest starts. The new-and-shipped counts match each task by its file name, because finishing a task moves its file into `archive/` and changes its path, so a moved task counts as shipped instead of as a new task; an exact path match wins when a repository holds both a live and an archived copy of one name.
- Update owns the scan lock inside a detached task that spans listing the repositories, harvesting, and storing, so a request that disconnects does not cancel the run: it keeps the scan lock and finishes storing every harvested result rather than releasing the lock while blocking harvests still run. Clicks that arrive while a scan runs share one follow-up scan, which starts after the running scan finishes and reads the repositories only after it starts, so repeated clicks run at most one more scan instead of one each. Add is the second path that takes the scan lock from a detached task: its insert and first harvest run in a spawned task that takes the lock itself and holds it until the last row is stored, and the request awaits only the handle to build its redirect, so a dropped request does not cancel the store, and a second Add or an Update waits on that same lock rather than racing it. Relocate is the third: its lookup, collision check, path write, and re-harvest run in a spawned task that takes the lock itself and holds it until the last row is stored, so a dropped request still stores the new folder's rows and a fresh scan stamp, and a second Relocate or an Update waits on that same lock rather than racing it. Confirm is the fourth: taking the held token and storing the held path run in a spawned task that takes the lock itself and holds it until the last row is stored, so a dropped request cannot abandon the store after the token is taken.
- A dashboard read claims its one-shot Update banner before rendering, and holds that claim in a guard that puts the slot back when the read is dropped before its render produces a response, as a cancelled navigation is; a completed render disarms the guard so the banner stays consumed, and a render error restores the slot at its call site. The flash store's lock is therefore synchronous, because a destructor cannot await and no lock is held across an await; a poisoned lock yields the store instead of panicking, so a render that panicked mid-claim does not lose the banner. A claim removes the slot under one lock acquisition, so however many reads name one token, only the first renders it.
- The server stops on SIGTERM or Ctrl-C: it stops accepting connections, gives a store that is already holding the scan lock up to a 4-second grace period to finish — an Update scan, Add's, Relocate's, or Confirm's detached store, or a Rescan, whichever holds it — closes the database, and then exits, leaving one second of the launcher's five-second stop window spare. The runtime teardown is bounded by the same deadline, so a blocking harvest cannot hold the process past it. That signal handling depends on tokio's `signal` feature.
- Static assets and templates resolve from the crate directory recorded at compile time, so `make run` works from this workspace root.
- Static asset URLs carry a content-derived version: `AppState` hashes every file under `task-viewer/static/` once at startup, the templates append that version as `?v=`, and `router` serves `/static` as immutable while the page routes stay `no-store`.
- Every read-only git subprocess is bounded: one helper drains stdout and stderr on their own threads while the child runs, wakes the moment stdout ends, and kills the child once the deadline passes. The deadline is 30 seconds by default and `TASK_VIEWER_GIT_TIMEOUT_SECS` changes it, within 1 to 600 seconds. A log or `cat-file` body instead streams through its parser as the child runs, with a watcher thread enforcing the same deadline, so a large history or object set is never held whole; the ref listing and enclosing path-prefix lookups stay buffered. A timeout fails the repository's scan instead of taking the `-C` or `updated` fallback, so a hung command cannot hold the scan lock or a blocking thread forever; an ordinary error stops the scan at the enclosing-repository probe and at a leave-day or pickaxe lookup inside a resolved enclosing repository, so only a lookup that runs and finds no qualifying commit takes the `updated` fallback.

## Direction

- Keep one viewer crate per tool, with `task-viewer` as the first.
- Add further viewers as sibling crates on this same local stack: one binary, loopback HTTP, Tera, SQLite in the home directory, and no harvested data in git.
- Grow the database only by raising `PRAGMA user_version` one step at a time.
